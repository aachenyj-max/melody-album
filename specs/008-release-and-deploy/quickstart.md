# 验收指南：SDD-07 MVP 发布

本指南用于继续 SDD-07 实施与验收。当前已完成本地照片直传实现、兼容迁移及部分 API 验证；实际结果以 `verification/` 为准，未执行的浏览器、目标宿主和发布步骤仍不得视为通过。验收门槛见 [release-gates.md](contracts/release-gates.md)，照片传输见 [photo-transfer.md](contracts/photo-transfer.md)。

## 1. 前置核对

1. 在 `progress.md` 确认 SDD-00 至 SDD-05 和 SDD-06 技术条件的证据。2026-10-08 用户明确不等待 SDD-06 真人试用；样本仍为 0，技术门槛继续核对。记录实际 Git 提交和工作区状态。
2. 对照 `AGENTS.md`、`.env.example`、SDD-05/06 契约核对用户端 demo、fal.ai API 与 QQ mock 边界。准备 1 张、9 张及单张接近 10 MiB 的真实照片；测试内容不提交到仓库。
3. 只读核对目标 Vercel 团队、项目、生产域名/分支、套餐、Node 版本、Function 时限、运行区域、部署保护和已有可用部署；核对 Supabase 项目、私有 bucket、相册及工作台的表/RLS/授权。记录标识和配置存在性，不打印密钥值。
4. 先按当前 `node_modules/next/dist/docs/` 核对 Route Handler、环境变量和部署约定，再改代码。核对 [research.md](research.md) 的 Vercel 4.5 MB 正文限制；当前大图经应用函数上传/下载的路径必须按照片传输契约硬化。

## 2. 本地硬化与质量门槛

1. 按照片传输契约完成签名直传、小体积提交和鉴权后短时读取；旧的已保存相册仍能打开。用 1 张、9 张、单张接近 10 MiB、合计接近 50 MiB 分别执行 07 保存与 08→09 刷新；浏览器网络面板确认大图只发往私有 Storage，应用函数请求/响应未超过 4.5 MB。
2. 中断第 2 张上传、令 token 过期、删除一张已传对象、重复相同 requestId、同 requestId 改内容、再次打开旧相册。预期为保留表单与有效音乐、按照片重传、冲突提示、最多一个 `ready` 相册和旧照片可读；失败/孤立对象不得进入列表。
3. 用隔离的超过 24 小时 `pending/failed` 样本验证相册清理：缺失或错误的 `CRON_SECRET` 被拒绝，正确调度仅清理目标对象与记录，失败可重试；`ready` 相册和另一身份对象保持完好，并记录目标宿主的实际调度结果。
4. 两个隔离的浏览器身份互相请求保存、列表、详情和照片；预期交叉访问为 404/拒绝，不返回另一人的相册或短时照片地址。未配置/错误内部口令时不能读取工作台或运行；维护 token 不能登录人类界面。
5. 在拟发布提交执行并记录全部输出摘要：

   ```powershell
   npm run format
   npm run lint
   npm run tscheck
   npm run build
   ```

   前两项可能修改文件；运行后检查 `git diff` 与 `git status`，确保记录的提交、待发布构建和最终文件一致。任一失败则修复后重新运行受影响检查，不能记录为通过。

## 3. 用户端主链路与状态

1. 使用一组真实照片在浏览器完成 01→02→03→04→05→06→05→07→08→09。修改记忆理解，检查 AI 生成/推荐来源、等待音乐、单一声音、手动播放/暂停、调整后的版本、07 保存表单、08 新记录、09 相同标题/日期/照片/短句/音乐。刷新 08 和 09 再核对，记录相册 ID（不可记录私有照片 URL）。
2. 在 AI 仍生成时进入 05：等待音不得被标为成品，只有可播的最终 AI 或 QQ mock 才能进入 07。阻止自动播放后可手动开始；退出播放声音停止。
3. 分别演示正常生成、慢响应、AI 失败但 QQ mock 可播、保存失败、历史读取失败。每类记录真实状态和至少一个可执行的继续、重试或返回动作；AI 失败路径仍完成选择、播放、保存、刷新查看。真实 fal.ai 调用与本地 WAV/演示拦截分别记证据，不能混算。
4. 在 320、375、430 px 宽度与较大字体下逐页核对 01–09 的布局、层级、配色、字体、图片位置、按钮文案、主要热点及无横向溢出，共 27 个视口组合。仅 01、08 显示底部导航；07 保存进入 08、08 卡片进入 09。05“查看 AI 理解”文案与保存热点的已知差异按 SDD-04/05 决策单独记录。

## 4. 工作台与安全

1. 按 SDD-06 `quickstart.md` 与已完成技术证据抽查生产口令关闭/错误/正确、测试运行、重跑、对比、用户端隔离和 30 天清理；确认维护调度至少在线上自动执行一次，不能只依赖手动调用。真人试用不阻断本轮发布。
2. 检查公开页面、浏览器 bundle、网络响应和错误信息。允许出现 Supabase URL/publishable key 和当前用户被授权的短时照片地址；`SECRET_KEY`、`DEMO_SESSION_SECRET`、`FAL_KEY`、Pi key、工作台口令/维护令牌、其他用户的照片地址及私有记录出现次数须为 0。
3. 记录真实 Agent 是否已验证。缺 Pi 凭证时用户端与工作台 demo 可以按既有契约验收，但必须标“真实 Agent 未验证”；QQ 始终标 mock；fal.ai 只凭实际 API 成功记录真实服务通过。

## 5. 待发布构建、正式发布与恢复

1. 在平台受保护配置中填入生产变量，核对变量名、作用环境与存在性，不导出值到仓库。`NEXT_PUBLIC_` 两项须在构建前正确设置；服务端密钥不加该前缀。`WORKBENCH_PUBLIC_ORIGIN` 使用正式 HTTPS 域名；本地 loopback `FAL_PROXY_URL` 不可照搬云端。
2. 确认目标团队、项目、提交和环境后，创建不自动指向正式域名的生产配置构建。保存部署 ID、URL、提交、配置版本和构建结果。在该 URL 重跑第 2–4 节适用项，特别是大图、用户隔离和生产函数时限。
3. 待发布构建全部通过后，将**同一部署 ID**指向正式域名；若平台要求重建，应重新验证新构建，不能复用旧证据。正式域名再跑至少一次完整主链路、跨身份照片检查、工作台拒绝访问和维护调度检查，并查看关键错误日志。
4. 记录前一个已验证可用部署 ID。若有生产故障，按平台恢复到该版本，再检查正式域名、相册读取、环境变量、Supabase schema/Storage 兼容和定时任务；记录实际恢复结果。平台部署回滚不会自动恢复数据库或变量。首次发布若没有前一个可用部署，明确写“无可回滚前版”，不能宣称回滚已验证。
