# 私有照片传输契约（发布硬化）

本契约在 SDD-05 保存语义不变的前提下，使最多 9 张、单张 10 MiB、合计 50 MiB 的原图不经过 Vercel Function 请求或响应正文。实施前核对已安装 Next.js 指南和 Supabase JS 版本；路径可保持现有 API 风格，但下述身份、大小、幂等和状态语义不可省略。

## 1. 初始化上传

`POST /api/albums/upload-intent`：同源、当前相册会话、`no-store`。请求为小体积 JSON，包含既有 `contractVersion`、`requestId`、保存快照以及按显示顺序排列的照片清单（文件名、MIME、字节数、内容摘要）；不得包含图片二进制、客户端 owner 或 bucket/path。服务端重新校验 SDD-05 标题、日期、短句、记忆/音乐来源与可播资格，并验证照片 1–9 张、单张 ≤10 MiB、合计 ≤50 MiB。仅服务端生成 `albumId` 和每张 `storagePath`，保留同一次 requestId 的摘要与 `pending` 状态。

成功响应返回 `albumId`、`requestId`、每张待上传项的固定索引、路径与仅供该路径的短时签名上传 token，以及已存在且与摘要一致的项状态。签名 URL/token 有过期时间，不写入日志、浏览器长期存储或验收文件。无身份 401、跨源 403、输入无效 400/413、同 requestId 不同摘要 409、服务不可用 503；所有响应只含可读错误码和脱敏文案。

浏览器用已有 Supabase JS 对私有 `memory-album-photos` bucket 执行 `uploadToSignedUrl`；单张上传直接去 Storage，应用函数不接收原图。签名创建默认不允许覆盖已有对象；重试只对尚未完成的固定路径重新签发。若使用可续传上传，也要沿用相同身份、路径、大小和结果校验，不改变相册 API 的最终语义。

## 2. 完成保存

`POST /api/albums` 对新流程接受小体积 JSON：既有保存快照、`requestId`、`albumId` 与按序照片清单；旧 multipart 输入可在兼容期保留，但目标环境不能依赖它通过大图验收。服务端重新确认当前身份与初始保存记录匹配，并逐一核对私有对象存在、路径归属、实际大小、类型、文件头与内容摘要；不能相信浏览器的 `uploaded`、`playable` 或 owner 布尔值。

核对通过后沿用现有相册照片、音乐版本、推荐和运行记录写入，最后把相册标为 `ready`。只有 `ready` 可出现在列表和详情。成功返回现有 `{ albumId, alreadySaved }`，首次 201、同一 requestId/摘要重试 200 且同一 albumId。正在处理返回明确的可重试状态；不同摘要的同 requestId 返回 409；对象缺失/不符返回可重传对应照片的错误，不产生假成功。失败保留本次表单与有效音乐，服务端清理或隔离残留对象和未发布记录。

## 3. 私有照片读取

保留现有 `GET /api/albums/{id}/photos/{index}` 作为稳定的相册照片入口。每次请求先按当前会话、相册 owner、`ready` 状态及索引校验；无权或未知返回 404，不透露存在性。合法请求只返回短时私有 Storage 读取地址（例如带 `private, no-store` 的临时重定向），不在函数响应中传原图。令牌过期后重新请求原入口；不把 Storage 路径或长期密钥写入列表/详情 DTO。已保存的旧照片沿用原路径，09 号页仍可读取。

## 4. 边界与验收

- 用 1 张、9 张、单张接近 10 MiB 和总量接近 50 MiB 的真实照片分别保存；浏览器到应用函数的请求和响应均低于 4.5 MB，原图只传到私有 Storage。
- 同 requestId 同内容重复、改内容冲突、上传中断、token 过期、部分照片缺失、对象内容不符和保存后刷新各有准确状态；`ready` 相册最多一条。
- 两个不同身份互相访问上传初始化、完成、列表、详情与照片入口，均不返回对方的内容或有效签名 URL；公开 bucket 访问失败。
- 验证旧版已保存相册仍可读；受 `CRON_SECRET` 保护的维护入口定期清理超过 24 小时仍为 `pending/failed` 的相册及其私有照片，只接受服务端校验的相册 ID，不影响 `ready` 相册或其他用户对象。清理失败需可重试并列入发布限制。
- 音乐只接受本次已验证可播的 AI 或 QQ 演示成品；等待音乐、元信息和失败候选不能因上传成功而被保存。
