# 功能规格：创建相册的连续 Agent 对话

**Feature Branch**: 当前 `master`；本轮仅规划，未新建开发分支
**Created**: 2026-10-09
**Status**: 已澄清，待实现
**Input**: 用户要求 02 上传和 03 理解像 GPT/Claude 一样真实连续聊天，取消预设假对话，后续回复不覆盖之前结果；通过 grill-me 逐项确认以下行为。

## User Scenarios & Testing

### User Story 1 - 根据照片连续聊出记忆与音乐方向（Priority: P1）

用户上传照片，Agent 先给出简短、可纠正的观察，再根据上下文追问。用户补充故事、纠正误解或说“你来决定”，双方消息持续追加，可以向上查看历史。

**Why this priority**: 直接解决假对话和覆盖上一轮回答的问题。
**Independent Test**: 上传照片后连续交流五轮，验证 Agent 引用早先补充和纠正，且历史消息内容与顺序不变。

**Acceptance Scenarios**:
1. **Given** 尚未上传照片，**When** 打开创建页，**Then** 只有真实欢迎引导，不伪造用户故事或看图结果。
2. **Given** 已成功上传有效照片，**When** 首轮理解完成，**Then** 追加基于实际照片的简短观察，并在有关键不确定性时最多追问一个问题。
3. **Given** 已有对话，**When** 用户补充故事或纠正“这是毕业，不是旅行”，**Then** 保留前面的消息，追加新消息和真实回应，后续理解采用纠正。
4. **Given** 用户不想选择曲风，**When** 说“你来决定”，**Then** Agent 给出理由清楚的建议供确认，不强迫完成固定问卷。

### User Story 2 - 确认最新音乐方向后再生成（Priority: P1）

信息足够时，Agent 在消息流里追加音乐方向确认卡，概括记忆、情绪、曲风与编曲方向。用户可以继续聊，或点击“按这个生成”。

**Why this priority**: 对话必须明确交接到现有生成、播放、保存流程。
**Independent Test**: 获取确认卡后继续修改情绪，再获取新版卡；旧卡可读但不可生成，新卡确认后进入 04。

**Acceptance Scenarios**:
1. **Given** 信息足够，**When** Agent 提出方向，**Then** 追加确认卡，而非自动开始生成音乐。
2. **Given** 有可确认卡，**When** 用户发送新消息，**Then** 原卡标记待更新，本轮处理完成前不能生成；新版卡出现后原卡标记已更新。
3. **Given** 最新卡与当前照片和已处理消息一致，**When** 点击“按这个生成”，**Then** 04 接收该版本的记忆、音乐方向和照片，继续 04→05→07→08。
4. **Given** 旧卡或存在未处理的新输入，**When** 尝试生成，**Then** 明确拒绝使用旧理解，不影响历史可读性。

### User Story 3 - 刷新和离开后继续同一段对话（Priority: P1）

每次创建相册有独立对话。刷新、离开再返回或浏览器重新打开后，在原会话下恢复照片、消息、最新卡和处理状态；明确新建才开启新对话。

**Why this priority**: 仅存在页面内存里的聊天无法支持真实持续创建。
**Independent Test**: 两个独立创建草稿分别聊三轮，刷新和离开后恢复指定草稿，验证上下文不混用。

**Acceptance Scenarios**:
1. **Given** 已保存一段对话，**When** 刷新或离开再返回，**Then** 按原顺序恢复全部已接收消息、当前照片和卡片状态。
2. **Given** 正在处理一轮，**When** 刷新，**Then** 显示服务端真实处理状态；中断时提供重试，不凭空出现成功结果。
3. **Given** 原对话仍存在，**When** 点击“创建新相册”，**Then** 新建独立对话，原对话不被覆盖；不新增专门聊天历史列表。
4. **Given** 另一位访客的草稿链接，**When** 当前会话打开，**Then** 无法读取照片、消息或确认卡。

### User Story 4 - 修改照片和失败时保留已聊内容（Priority: P1）

对话期间增删照片形成变更消息，Agent 基于当前照片重新理解。回复失败时保留用户刚发的消息和全部历史，支持重试。

**Why this priority**: 保障真实调用和可变照片下的内容一致性。
**Independent Test**: 有卡后增删照片，模拟回复失败再重试，验证仅一个用户消息、完整历史、正确照片与新版确认卡。

**Acceptance Scenarios**:
1. **Given** 已有历史和确认卡，**When** 增删照片，**Then** 追加明确的照片变更记录，旧卡待更新，重新理解就绪前禁止生成。
2. **Given** 用户消息已被接收，**When** Agent 超时或失败，**Then** 本轮显示失败与“重试”，用户消息不丢失。
3. **Given** 本轮失败，**When** 重试成功，**Then** 不重复插入用户消息，只追加成功的 Agent 回应。
4. **Given** 修改照片时旧请求还未完成，**When** 旧回应迟到，**Then** 不作为当前理解或可生成卡。

### Edge Cases

- 零张照片可以保存文字并聊天，但必须明确没有图片可观察；不能形成可生成卡。删除至零张同样禁用生成。
- 无效照片、超出九张、读取或上传失败：不提交无效照片变更；保留历史和未发送文字。
- 输入尚未被服务端接收时断网：保留输入并提示未发送；重发使用同一消息标识。
- 双击发送、重试重复提交、双标签页修改：不能重复消息、并发污染上下文或确认过期卡。
- 相同草稿刷新中断、模型结果校验失败、存储失败：错误明确可恢复；不以预设回答伪装真实成功。
- 删除照片后历史保留变更说明和文字，不再向 Agent 注入已删除图片。
- 长对话达到处理容量：历史仍可读，明确提示继续限制；不得默默丢失早先纠正或关键约束。
- 会话身份丢失或草稿到期：说明不可恢复原因，不冒充恢复；明确新建。

## Requirements

### Functional Requirements

- **FR-001**: 02 和 03 必须作为同一独立对话的上传/理解状态，保持已有入口和后续页面顺序。
- **FR-002**: 禁止渲染预设用户消息、未经真实理解的看图结论或固定修正问题；欢迎和处理中提示可为静态界面文案。
- **FR-003**: 成功上传照片后自动发起首轮观察；每次回复最多提出一个关键追问，无固定问题和轮数。
- **FR-004**: 成功接收的用户消息、照片变更、Agent 回应与卡片必须逐条追加并保留顺序和内容；禁止新回应覆盖旧回应。
- **FR-005**: Agent 必须使用同一草稿内已成功处理的对话、当前照片和用户纠正，区分观察和推测，允许用户委托其推荐方向。
- **FR-006**: 信息足够时追加记忆、情绪及音乐方向确认卡；用户明确确认前不调用音乐生成。
- **FR-007**: 继续聊天或变更照片立即令旧卡待更新；新版卡就绪后旧卡标记已更新，且只有最新有效卡可生成。
- **FR-008**: 确认卡必须绑定其所依据的照片和消息版本；有未处理输入、错误或零张照片时禁止生成。
- **FR-009**: 确认交接必须携带当前卡的实际记忆、音乐方向和照片，接续现有生成、播放和保存流程，不丢失用户曲风要求。
- **FR-010**: 每次创建相册对应独立对话，保存照片、已接收消息、卡片历史、最新理解及处理状态。
- **FR-011**: 在相同有效会话下刷新、离开返回或重新打开后恢复原对话；“创建新相册”开启新对话并保留旧草稿。
- **FR-012**: 草稿内容仅由归属会话访问，不向其他访客泄露；第一版不提供单独聊天历史列表。
- **FR-013**: 有效照片变更必须追加变更记录并重新理解当前照片；过期回复不得更新当前理解。
- **FR-014**: 单次选择保持现有照片格式、单张/总大小约束与 1–9 张生成门槛；上传失败不得伪造成功变更。
- **FR-015**: 回复失败必须保留已接收的本轮用户消息与历史，展示失败与重试；重试不得重复用户消息。
- **FR-016**: 重复操作、处理中刷新、双标签页和迟到请求必须保持消息、最新卡和当前照片一致；错误和中断不得静默返回 demo。
- **FR-017**: 保留 02/03 的手机外壳、标题、返回、照片区域、白底玻璃气泡、绿色点缀和底部输入风格；用户此次明确授权消息区连续滚动、卡片追加及取消固定示例建议，覆盖原稿相关局部结构/文案。
- **FR-018**: 在 320/375/430 宽度、较大字体和软键盘场景下，消息可读可滚动，输入和当前操作可达；阅读旧消息时不得被新回复强制拉到底部。

### Key Entities

- **创建对话草稿**：归属会话、独立标识、当前照片集合、版本、处理状态与恢复位置。
- **对话消息**：身份、角色、内容、顺序、接收状态；照片变更记录也属于消息。
- **处理轮次**：关联输入消息和照片版本，处理结果、失败与重试状态。
- **音乐方向确认卡**：记忆概要、情绪、曲风/编曲、依赖版本、待更新/已更新/可确认/已确认状态。
- **确认快照**：用户确认的卡片与照片版本，作为后续音乐生成和保存的稳定输入。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 一段五轮真实对话中，全部已接收消息按原顺序可见，覆盖和重复消息数均为零；后续回应遵循用户第二轮提出的纠正。
- **SC-002**: 两组不同照片与故事的真实会话分别得到与实际内容相关的观察；每轮最多一个关键追问；“你来决定”能获得可确认建议。
- **SC-003**: 同一对话连续刷新三次、离开返回一次、重新打开一次，已接收消息、照片和卡片版本完全恢复；两段草稿不混用。
- **SC-004**: 修改情绪、增加照片、删除照片三个场景均令旧卡不可生成；最新卡确认后 04 的方向和照片与之逐项一致。
- **SC-005**: 超时、服务不可用、无效结果三种失败后均能重试恢复，本轮用户消息仅一条；旧理解不会误用于生成。
- **SC-006**: 双击发送、重复重试、处理中刷新和双标签页四类场景均无重复消息、无过期卡确认和迟到结果污染。
- **SC-007**: 320/375/430 宽度及较大字体场景无横向溢出，长消息和确认卡可读，键盘弹出后输入及发送可达；02→03→04 和返回恢复通过。
- **SC-008**: 两个不同访客会话互读草稿、照片、卡片和执行确认均被拒绝；当前会话可完成最新卡确认→生成→播放→保存→列表回读。

## Assumptions

- 2026-10-09 grill-me 的七次选择均已接受推荐方案；无需重新询问同一产品决策。
- 同一有效浏览器会话内恢复，不承诺匿名访客跨设备恢复；浏览器仅保留草稿恢复标识，不是内容唯一存储。
- 首版整段回复即可，不以逐字流式输出为交付条件；不提供消息编辑、删除、分叉、全局历史列表或已保存相册的聊天重构。
- 当前草稿默认保留自最后活动起 30 天，过期明确提示；保存相册的独立持久化不受草稿到期影响。这是实施默认值，不是已确认的永久保留承诺。
- 当前已有音乐生成能力及明确标识的 QQ mock 保持原有边界。真实调用验收与故障夹具结果分开记录，不替代真人试用统计。
- 02/03 局部交互覆盖以本规格为准；01、04–09 不进行无关视觉改版，06 原创建音乐调整流程保留。
